2. Relational Schema & Integrity Constraints

Formal table definitions with Primary Keys, Foreign Keys, NOT NULL, UNIQUE, and CHECK constraints.

users Master Entity
  • user_id (INTEGER, PRIMARY KEY)
  • full_name (VARCHAR(100), NOT NULL)
  • email (VARCHAR(120), UNIQUE, NOT NULL)
  • phone (VARCHAR(20), NOT NULL)
  • role (VARCHAR(20), CHECK role IN ('PASSENGER', 'ADMIN'))
  • created_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
buses Fleet Entity
  • bus_id (INTEGER, PRIMARY KEY)
  • bus_number (VARCHAR(30), UNIQUE, NOT NULL)
  • operator_name (VARCHAR(100), NOT NULL)
  • bus_type (CHECK IN ('AC Sleeper', 'Volvo Multi-Axle', ...))
  • total_seats (INTEGER, CHECK > 0 AND <= 60)
  • rating (NUMERIC, CHECK >= 1.0 AND <= 5.0)
routes Network Entity
  • route_id (INTEGER, PRIMARY KEY)
  • source_city (VARCHAR(80), NOT NULL)
  • destination_city (VARCHAR(80), NOT NULL)
  • distance_km (NUMERIC, CHECK > 0)
  • estimated_duration_hours (NUMERIC, CHECK > 0)
  • UNIQUE (source_city, destination_city)
  • CHECK (source_city <> destination_city)
trips Associative Entity
  • trip_id (INTEGER, PRIMARY KEY)
  • bus_id (FK → buses.bus_id, CASCADE)
  • route_id (FK → routes.route_id, CASCADE)
  • trip_date (DATE, NOT NULL)
  • departure_time (TIME, NOT NULL)
  • arrival_time (TIME, NOT NULL)
  • fare (NUMERIC, CHECK fare > 0)
  • status (CHECK IN ('SCHEDULED', 'COMPLETED', 'CANCELLED'))
bookings Transaction Entity
  • booking_id (INTEGER, PRIMARY KEY)
  • pnr_number (VARCHAR(20), UNIQUE, NOT NULL)
  • user_id (FK → users.user_id, RESTRICT)
  • trip_id (FK → trips.trip_id, RESTRICT)
  • booking_timestamp (TIMESTAMP, CURRENT_TIMESTAMP)
  • total_seats (INTEGER, CHECK total_seats > 0)
  • total_amount (NUMERIC, CHECK total_amount >= 0)
  • booking_status (CHECK IN ('CONFIRMED', 'CANCELLED'))
booking_passengers Seat Allocation Detail
  • ticket_id (INTEGER, PRIMARY KEY)
  • booking_id (FK → bookings.booking_id, CASCADE)
  • seat_number (INTEGER, CHECK > 0 AND <= 60)
  • passenger_name (VARCHAR(100), NOT NULL)
  • passenger_age (INTEGER, CHECK >= 1 AND <= 120)
  • passenger_gender (CHECK IN ('Male', 'Female', 'Other'))
  • UNIQUE (booking_id, seat_number)

3. Normalization Analysis (1NF → 2NF → 3NF)

Elimination of redundant storage, insertion anomalies, update anomalies, and deletion anomalies.

First Normal Form (1NF) - Atomicity

Requirement: Each attribute must hold atomic (indivisible) values, and no repeating groups exist.

Implementation: In a legacy flat system, multiple passenger names and seats might be comma-separated strings inside a single booking record. In our schema, passenger allocations are completely extracted into individual atomic rows in the booking_passengers table. Each row stores exactly one passenger name, age, gender, and seat number.

Second Normal Form (2NF) - No Partial Dependency

Requirement: Must be in 1NF, and all non-key attributes must be fully functionally dependent on the entire primary key (no partial dependencies on a subset of a composite key).

Implementation: Rather than using a composite primary key like (bus_number, source_city, trip_date) where route details (distance, duration) only depend on the source and destination, we decomposed the schema into independent entities with surrogate primary keys (bus_id, route_id, trip_id). Route distance depends solely on route_id, not on the trip or bus.

Third Normal Form (3NF) - No Transitive Dependency

Requirement: Must be in 2NF, and no non-key attribute is transitively dependent on the primary key ($X \rightarrow Y$ and $Y \rightarrow Z$ where $X$ is the primary key).

Implementation: In the trips table, we store only route_id and bus_id. We do not store operator_name or distance_km in trips, because that would create a transitive dependency (trip_id → bus_id → operator_name). Whenever trip details are required, we query via relational JOINs or pre-defined views (vw_trip_schedule).
